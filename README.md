# PA2_Group13
Concurrent Hash Table

This project implements a concurrent hash table for PA#2. Each bucket of the table is a singly linked list of records containing a cached Jenkins “one-at-a-time” hash, a fixed-size name (up to 49 characters plus terminator), a salary, and a `next` pointer. The table is protected with an array of per-bucket reader–writer locks constructed from POSIX semaphores (OSTEP style). Operations supported by the driver are: `insert`, `update`, `delete`, `search`, and `print`. A `threads` line is accepted for compatibility with the instructor’s file format but we still spawn one worker per command to match the required deterministic start order.

Deterministic ordering is enforced with a single condition variable and a counter. When thread *i* starts, it waits until the shared “current turn” equals *i*. Immediately upon starting, it signals the next turn before it performs the expensive work (hashing, locking, etc.). This makes the log and console output predictable for grading while still allowing true overlap among active operations once they have begun.

For synchronization, writers (`insert`, `update`, `delete`) acquire exactly one bucket’s write lock, perform their list mutation, and release it. Readers (`search`) acquire the bucket’s read lock, examine the list, and release. The key design point is the `print` operation: it must produce a consistent snapshot of the entire table and, per the rubric, it should “grab every lock at once” and have that count as one acquisition. Our `print_table` does exactly this. It acquires all bucket read locks in ascending index order (0 to N–1) without emitting per-bucket log messages, records a single consolidated line in `hash.log` indicating that all read locks have been acquired, enumerates and copies every record into a temporary vector, then releases all read locks in reverse index order (N–1 back to 0) and logs one matching consolidated release line. Acquiring in a fixed global order and releasing in the reverse order prevents deadlock. Writers never hold more than one lock at a time, so there is no cyclic wait; they simply block while `print` holds the read locks and resume immediately after the snapshot completes.

To make the logging meet the grading requirement (“one acquisition” per `print`), the lock helpers accept a `priority` integer that is attached to log lines. We treat any negative priority as “silent”; a small wrapper (`maybe_log`) checks the priority and suppresses the log message if it is negative. During `print`, we acquire and release each bucket’s lock with a negative priority (no spam), and then write exactly one human-readable line such as “READ LOCK ACQUIRED (ALL BUCKETS)” and a matching line on release tagged with the thread’s real priority. All other operations pass a non-negative priority and therefore continue to log their normal messages such as “WAITING FOR MY TURN”, “AWAKENED FOR WORK”, and “WRITE LOCK ACQUIRED/RELEASED.”

The snapshot that `print` produces is deterministic. While all read locks are held, we traverse each bucket and copy out tuples of (hash, name, salary) into a temporary array. We then sort that array first by hash and then by name to stabilize the output across runs, and we print the section header “Current Database:” followed by one line per record in the form “hash,name,salary”. Caching each record’s hash avoids recomputing it while locked and ensures the ordering is stable even if names are revisited later.

Input is read from a CSV file named `commands.txt` by default; each nonempty, non-comment line has the shape `op,arg2,arg3,priority`. Inserts and updates use arg2 as the name and arg3 as the new salary. Deletes and searches use arg2 as the name. The `print` line carries a priority in the final field; any intermediate fields on that line are ignored but kept to match the instructor’s examples. The driver prints human-readable confirmations for each command. Insertions report that a record was inserted and echo the record contents. Updates report the old and new salary for the same record. Deletes report the full record that was removed. Searches either print “Found: hash,name,salary” or “<name> not found.” The `print` command prints the sorted snapshot described above.

We build and test on Windows using MSYS2’s MinGW-w64 environment (the terminal prompt shows “MINGW64”). The project uses `gcc` with C11, pthreads, and winpthreads. If building manually you will compile the three sources—`chash.c` (the main threaded driver), `HashFunctions.c` (hash, core table ops, and print), and `locks.c` (reader–writer locks and logging)—and link with pthreads; our Makefile in the repository does this automatically. Running the executable with no arguments reads `commands.txt`; you may also pass a different commands file path as the first argument if your grader allows it. A log file named `hash.log` is created in the working directory and contains timestamped entries of lock activity and consolidated `print` events.

Regarding correctness properties: the table never mutates without holding the appropriate bucket’s write lock. Readers never see partially linked nodes because they only traverse while holding the read lock that fences writers. `print` produces a consistent snapshot because it holds read locks on **all** buckets while copying out entries; this blocks writers momentarily, which is the expected tradeoff for consistency. Deadlock is avoided by the fixed global order in which `print` acquires locks and by the fact that writers take at most one lock. Starvation is unlikely in practice because `print` holds the locks only as long as it takes to copy the lists; after that, writers run freely again. Finally, output is deterministic because start order is enforced with a condition variable and because snapshot rows are sorted before printing.

If a grader needs a brief mapping to the rubric: the project compiles with a Makefile and runs to completion. Inserts, searches, updates, and deletes are protected by per-bucket locks and report the correct console messages. `print` acquires all locks in bulk (one acquisition as seen in the log), prints the database sorted by hash and name, and then releases the set in bulk (one release log). The lock messages appear in `hash.log`, and the final table output matches the deterministic ordering the rubric expects.

If you need to adjust parameters, the hash table size and the logging behavior are easy to tune in `chash.c` and the lock helpers. Setting the global log file pointer to null disables logging entirely without changing synchronization behavior.
